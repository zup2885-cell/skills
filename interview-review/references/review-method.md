# 逐题复盘与跨场比较

## 输入和证据

先记录来源：逐字稿 transcript、用户回忆 recall、局部笔记 notes。保留原始文字，用 `source.text.splitlines()` 的一基行号定位。没有时间戳也可引用行号，不编造时间。

用户回忆“他好像不满意”是主观感受；只可记成“用户回忆/感受”，不是面试官原话或淘汰理由。摘要、缺失片段、角色不明时降低判断范围。无法识别双方，不给归因结论。

可保留公司和目标岗位便于本人检索。姓名、联系方式和内部敏感标识只在确有复盘需要时保留；对外分享另做脱敏副本，不覆盖原记录。

## 逐题判断

每个有价值的主问题与追问各列一个问题项，可共用 topic_key。每项包括：

- 问题与追问：尽量保留原问；整理过的文字注明是整理。
- 回答摘要：只概述用户当时实际说了什么；缺答就写“未记录回答”。
- 有效点：具体到回答里的行为、判断、证据。
- 缺口：是知识不准、事实没交代、职责不清、缺少结果，还是表达顺序影响理解。
- 更稳的答法：一段能开口讲的文字，通常 60—90 秒；时长按题目需要调整。没有个人事实就明确留待补项。
- 证据：至少一条真实材料引用，指出行号；引用不到时不能伪造证据项。

状态只表示本次回答的证据，不是能力评级：

| 状态 | 含义 |
| --- | --- |
| strong | 回答提供了与本题相关的充分证据 |
| partial | 有相关内容，但仍有明确缺口 |
| gap | 记录显示本题关键内容缺失或错误 |
| unknown | 未答、漏录或证据不足，无法判断 |

技术、财务、法律等专业正确性无法核实，写待核实。用户材料里的指标也不因出现过就当作外部核验通过。

## 回答模板与个人案例

只保留本人的真实经历。一个案例可对应多题，但要写清来源题号、适用考点和还缺的证据。不同公司、不同任职时期的事实不能拼成一段新经历。

STAR 是可选表达工具，不要求每题都套。概念题先解释概念；方案题说明假设与取舍；个人经历题要说清背景、自己做了什么、结果如何验证。没有结果数据时，说已有的验证事实或待补内容，不硬凑增长率。

不要根据文字材料诊断人格、心理疾病或推断隐私特征；只分析可观察的作答行为。

## 跨场归纳

topic_key 用稳定的 ASCII 小写键，如 `content-ops.project-ownership`；它是语义分类键，不是关键词。换岗位后，即使都问“增长”，也可能需要新键。

问题库按不同 session_id 统计出现次数。同场 3 个追问仍是 1 场。跨场疑似重复缺口至少需要 2 场中同 topic_key、同 gap_tag 的实际缺口证据；不能只看题目重复。

按面试日期比较，日期未知不判断前后。同日多轮若没有时间/轮次顺序依据，不宣称进步趋势。比较时显示每次状态与出处，不只给平均分。脚本的“多场缺口线索”是待人工复核的计数，不自动证明根因相同。

一次 strong 是新证据；之前暴露的缺口是否解决，需要结合最近同类回答及真实反馈复核。面试通过或失败可能受岗位匹配、HC、薪酬、竞争者等因素影响，不能把结果全部归因于作答。

## 下一场准备

只选最多 3 项，按目标 JD 的相关性、近期出现的关键缺口和时间成本排序，不仅按频次。每项写练什么、用哪个真实案例、做到什么算完成。没给下一场 JD 时标明“通用准备，待结合目标岗位调整”。

回填录用结果时保留原分析，并区分招聘方明确反馈与个人推测。结果变化不能倒推面试官当时真实想法。
